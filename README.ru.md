# SF2e Tactical Starship Combat

## Экспериментальная версия 0.17.1-dev.13

**Экспериментальная неопубликованная версия; устанавливайте только в тестовый мир после резервного копирования.** Каждое размещение Actor из мира или компендия на Sensor Map создаёт отдельную постоянную копию Actor в мире; исходный Actor остаётся шаблоном. У копий независимы HP, SP, состояния, эффекты, предметы и остальные системные данные. NPC-корабли и сложные опасности получают отдельные Combatant при публичном размещении или раскрытии. Приватные контакты остаются доступны только ведущему и не получают публичный Combatant до раскрытия; удаление контакта удаляет его копию и запись инициативы. Перетаскивание сохранено, публичное раскрытие требует подтверждения ведущего. Приватность **не проверена в настоящем Foundry с несколькими клиентами**. Лист персонажа в активном космическом бою позволяет занять или покинуть станцию. Карточка урона нативного Strike предлагает подтверждаемый ведущим Drone Block: выбрать дрон и конкретный удар, затем применить сопротивление штатной системой урона или разрешить вручную. Сопротивление равно половине уровня оператора с округлением вниз; дрон возвращается на 10 минут даже при сопротивлении 0. У возвращённого дрона отображается оставшееся время блокировки или недоступность времени мира. При Drone Shield Protocol ведущий подтверждает только ручное разрешение; существующий журнал дрона учитывает блокирования и ожидание Fetch and Fix для листа, а ведущий по-прежнему вручную определяет состояние щита и применяет эффект. Базовые возврат и 10-минутная блокировка не применяются. Неоднозначности Intercept Munitions и мин Pyrotechnics Drone при базовом автоматическом возврате требуют решения ведущего. Учёт действий и реакций не ведётся. См. `docs/work-in-progress-0.17.1-dev.13.md` и `docs/MANUAL-TEST-0.17.1-dev.13-ru.md`. ZIP устанавливается вручную; релиз не опубликован.

Модуль тактического космического боя для **Starfinder Second Edition** в **Foundry VTT 14**: корабли игроков и НИП, боевые станции, экипаж, опасности и отдельная зональная сенсорная карта.

Каждый персонаж сохраняет собственную инициативу и обычные действия. По умолчанию корабль игроков не получает отдельного хода; для корабля с критическим повреждением предусмотрено исключение ради проверки целостности корпуса.

> **Экспериментальный проект, разработанный с помощью ИИ.** Есть автоматические тесты и локальные проверки интерфейса. Сделайте резервную копию мира и сначала проверьте модуль на копии. Файлы системы не изменяются.

> **0.17.1-dev.9 — экспериментальная неопубликованная сборка.** Сделайте резервную копию и установите ZIP вручную: ссылка указывает на будущий релиз. Интеграция Toolbelt проверена по исходникам и моками, но не в настоящем Foundry. Объединённые, дополненные и разделённые карточки урона Better Chat не применяются к кораблям автоматически; см. `docs/work-in-progress-0.17.1-dev.9.md`. **Контакты Sensor Map не являются приватными для игроков.** Учёт действий и реакций не ведётся.

> **Неопубликованное исправление надёжности:** сенсорная карта сохраняет DOM-слой фона при замене частей и кеширует доступные данные акторов в пределах окна. Большие изображения отображаются через PNG-копию с пределом 4096 пикселей; обычные изображения, исходные файлы и пути не изменяются. Локальная проверка Chromium использовала настоящий PNG 8100 × 11700 и 360 объектов. Первичное декодирование всё ещё требует памяти; ограничения доступа к холсту могут привести к показу полного исходного изображения. Производительность в настоящем Foundry не проверена. Для незавершённого опознания есть явная кнопка восстановления Мастера; перед повтором разберите конфликт.

## PF2e + SF2e Anachronism

Тот же модуль можно использовать в **PF2e 8.6.0+** с установленным и активным **SF2e Anachronism 2.4.0+**, на Foundry v14. Anachronism обязателен только в PF2e; в самостоятельной SF2e дополнительных модулей не требуется. Манифест поддерживает обе системы, а условная зависимость проверяется при запуске, чтобы не требовать PF2e-модуль в мире SF2e.

1. Установите официальный SF2e Anachronism из [релизов репозитория системы](https://github.com/foundryvtt/pf2e/releases).
2. Включите Anachronism и этот модуль, затем перезагрузите мир.
3. Используйте компендиумы папки **Tactical Starship Combat (PF2e)**. Их имена имеют суффикс `-pf2e`, ID соответствующих документов сохранены. Исходные SF2e-паки и UUID существующих миров не изменены.
4. Создавайте корабли через интерфейс модуля или импортируйте из PF2e-паков. Назначайте в экипаж персонажей PF2e: Computers и Piloting добавляет Anachronism через дополнительные навыки. Если навыки недоступны, модуль сообщает об этом, а не подменяет их другими.

Листы, станции, сенсорная карта, проверки, урон, инициатива критически повреждённого корабля и необязательная интеграция урона с Toolbelt используют namespace активной системы. Картинки и внутренние ссылки PF2e-паков ведут в PF2e-варианты. Приоритет имеют состояния самой PF2e; при наличии используются и дополнительные состояния Anachronism.

Это **не** конвертер миров между системами и не перенос уже импортированных SF2e-документов в PF2e. Сделайте резервную копию и используйте паки нужной системы. Выполняются статические проверки и мок-тесты; совместную работу в настоящем мире PF2e + Anachronism ещё нужно проверить в игре.

## Toolbelt и Workbench

Проверки корабля доступны через штатный `actor.getStatistic`. Адаптер предназначен для запросов Стойкости, Рефлекса и Воли через ссылки SF2e и **PF2e Toolbelt Target Helper** как у кораблей игроков на базе vehicle, так и у NPC-кораблей. Восприятие и сохранённые навыки используют тот же адаптер, что и лист корабля. Для спасброска корабля выбирайте **токен корабля**, а не члена экипажа.

Связующий слой сохраняет прежний метод поиска и дополняет его только для акторов с явной меткой корабля модуля. Обычные акторы, неизвестные характеристики и настройки сторонних модулей не изменяются. Проверки используют текущие данные экипажа и эффектов; системные модификаторы NPC сохраняются. Дополнительные броски и автоматическое применение урона не создаются.

При активном **PF2e Toolbelt** в сообщениях типизированного урона для кораблей модуля появляются две кнопки:

- **Урон через щиты**: расчёт корабельным движком, остаток после щитов переходит в корпус.
- **Напрямую в корпус**: щиты пропускаются, но применимые иммунитеты, сопротивления, уязвимости и Твёрдость сохраняются.

Штатные кнопки положительного урона (полный, половина, двойной и тройной) в строках корабельных целей тоже используют корабельный движок, по умолчанию через щиты. Множитель выбирается явно; **Shift** при применении открывает ввод числовой поправки. Типы и значения берутся из сохранённого броска, а не из присланной клиентом суммы. Для нескольких типов сначала учитываются защиты каждого типа, затем Твёрдость и переход щиты/корпус применяются один раз. Повторное применение того же броска сообщения к тому же кораблю защищено от повторного списания, в том числе при смене режима. Нужны активный ведущий и право изменять очки этого корабля.

Ручные ×2/×3 изменяют урон, но **не подтверждают критическое попадание**. Подтверждение попадания берётся из степени исходного сохранённого броска либо однозначного нативного результата урона атаки; критический успех спасброска/другой проверки не является критическим попаданием. Отсутствующие или противоречивые данные не подтверждают его. Собственный критический провал спасброска корабля тоже усиливает Compromised: существующая обработка спасбросков цели сохранена; неоднозначный случай Toolbelt следует проводить через явное нанесение урона Мастером, а не выводить из ×2. Типы урона, защиты и квитанции повторного применения сохранены.

Обычные акторы и штатное лечение сохраняют прежнее поведение. Личный **Блок щитом** Toolbelt не является действием корабельных щитов — используйте две корабельные кнопки. Общая строка со смешанным выбором кораблей и обычных акторов блокируется: используйте отдельные строки целей Toolbelt или выбирайте корабли отдельно. Невычисленный продолжительный урон, броски только лечения и сообщения с отдельным уроном по области этим связующим слоем не поддерживаются; применяйте их подходящим ручным способом. Состояние продолжительного урона автоматически не создаётся.

Карточки атак самого модуля сохраняют прежнюю кнопку **применения урона**. У новых связанных бросков скрыты дублирующие системные кнопки. Для старых сообщений, созданных до обновления, не применяйте урон обоими способами. После установки перезагрузите мир.

Изучены исходники Toolbelt **3.59.2** и Workbench **7.7.5**. Автоматизация заклинаний и существ Workbench не заменяет движок корабельных действий: автоматическое выполнение станций и CR-масштабирование корабельных данных не добавлены. Обязательных зависимостей от этих модулей нет. Мок-тесты и локальные проверки интерфейса не заменяют проверку интеграции в игровом мире.

## Установка

В **Add-on Modules → Install Module** вставьте ссылку на manifest:

```text
https://github.com/Huxtuntios/sf2e-tactical-starship-combat/releases/latest/download/module.json
```

Эта ссылка заработает после публикации обычного релиза, не помеченного как prerelease. Для конкретного выпуска или предварительного релиза после его публикации используйте:

```text
https://github.com/Huxtuntios/sf2e-tactical-starship-combat/releases/download/v0.16.0/module.json
```

Включите модуль в мире SF2e. Руководство есть в компендиуме **Guide / Руководство**.

При ручной установке создайте папку `Data/modules/sf2e-tactical-starship-combat/` и распакуйте **`module.zip` внутрь неё**. Файл `module.json` должен лежать непосредственно в этой папке. Автоматические архивы GitHub **Source code** предназначены для разработки, а не установки в Foundry.

Идентификатор модуля не меняется: `sf2e-tactical-starship-combat`.

## Быстрый старт

1. Создайте корабль игроков через **Starship Builder** либо преобразуйте актёра `vehicle` через контекстное меню. Обычные транспортные средства автоматически не преобразуются.
2. Импортируйте корабли НИП и опасности из браузера контента или компендиумов.
3. Перетащите персонажей на вкладку **Станции**, назначьте экипаж и посты.
4. Запустите мастер **Start Tactical Starship Combat**: корабли, экипаж, статусы обнаружения, опасности и объекты.
5. Бросьте инициативу как обычно. Действия доступны на сенсорной карте, во вкладке **Станции** и в отдельном окне **Действия станций**.

## Возможности

- **Две карты в одном бою:** обычная сцена корабля и отдельная зональная сенсорная карта с дальностью, курсом, областями и обнаружением.
- **Станции и экипаж:** пульт пилота, генератор, орудийная станция, сканеры, магический канал, пульт дронов и пользовательские станции. Отдельный менеджер показывает назначения и готовность.
- **Действия станций:** данные хранятся отдельно от интерфейса, проверки используют штатные средства SF2e. По умолчанию нарушения правил вызывают предупреждение; можно включить строгий режим. Неподдерживаемые способности остаются для ручного решения.
- **Корабельный урон:** щиты, корпус, иммунитеты, сопротивления, уязвимости, критическое повреждение, разрушение и целостность корпуса. Для учёта щитов используйте инструменты модуля, а не системные кнопки применения урона.
- **Опасности:** простые срабатывания и сложные рутины, ручные подтверждения ведущего или автоматический режим. Автоматизируются только поддерживаемые форматы правил.
- **Контент:** 74 корабля, 32 опасности, 37 действий, 17 орудий, 34 записи улучшений и три рамы; компендиумы на английском и русском. Для улучшений проверяются совместимость и вместимость станций, но не все их эффекты автоматизированы.
- **Оформление сенсорной карты:** цвета текста, арты и символы, отдельные изображения объектов и фон с прозрачностью, обесцвечиванием и размытием. Неопознанные контакты не раскрывают свои арты.
- **Темы окон:** все окна модуля используют клиентскую настройку «Тема интерфейса модуля»: «Как в Foundry», «Светлая» или «Тёмная». Предыдущий выбор светлой или тёмной темы сохраняется; другие клиенты независимы.
- **Длительность эффектов:** начало/конец определённого хода, несколько раундов, ручное подтверждение условия и напоминания о поддержании. Уклонение показывает потраченные действия; поддержание не тратит действия автоматически.
- **История и ограниченная отмена:** до 80 записей изменений модуля, видимых ведущему, с причиной, изменениями корпуса/щитов и переходами к объектам. Отменяется только ограниченный совместимый набор изменений, но не броски, затраты действий или раскрытая информация.
- **Интерактивные описания:** состояния отправляются в чат и перетаскиваются на персонажей с сохранением степени; урон бросается с нужным типом, без автоматического применения. Контекстные КС используют характеристики оператора, когда это однозначно следует из правил; отсутствующие и неоднозначные КС остаются для ручного выбора.
- **Удобство:** запоминание размеров окон и вкладок на клиенте, поиск по справочникам, улучшениям и истории.
- **Сетевая работа:** изменения проверяет и сохраняет активный ведущий; права на корабль и станцию перепроверяются. `socketlib` не нужен.
- **Признак `starship`:** хранится и отображается на английском независимо от языка интерфейса.

## Ограничения

Полный многопользовательский сценарий в живом Foundry ещё требует проверки. Штатное применение урона SF2e не учитывает щиты модуля. Многие улучшения и способности НИП требуют решения ведущего. Отмена не откатывает несколько документов атомарно: сохранённое намерение и квитанция Actor позволяют завершить историю после частичного сбоя только при совпадении состояния Actor и Combat. Незавершённую квитанцию нельзя перезаписать другим Undo, а ожидающую запись — удалить при лимите 80. Отмена HP/SP, урона и критических состояний запрещена. Условия эффектов и нестандартные перестановки инициативы могут потребовать ручной корректировки. Для изменения состояния нужен активный ведущий.

## Разработка

Нужны **Node.js 22.13+** и npm. Bash и отдельный архиватор не требуются.

```sh
npm ci
npm run format
npm run check
npm run build:release
```

В `dist/` появятся `module.json`, `module.zip`, контрольные суммы и заметки к выпуску. Для локальной проверки интерфейса:

```sh
npx playwright install chromium
npm run test:ui
```

Скомпилированные компендиумы, зависимости и архивы не коммитятся. Исходные данные находятся в `data/`; перед сборкой компендиумы создаются заново. GitHub Actions проверяет проект и собирает файлы релиза.
