# SF2e Tactical Starship Combat

[English](README.md) · [Руководство](docs/guide-ru.md) · [Релизы](https://github.com/Huxtuntios/sf2e-tactical-starship-combat/releases) · [Сообщить об ошибке](https://github.com/Huxtuntios/sf2e-tactical-starship-combat/issues)

Модуль тактического космического боя для **Starfinder Second Edition** в **Foundry VTT 14**: корабли игроков и НИП, боевые станции, экипаж, опасности и отдельная зональная сенсорная карта.

Каждый персонаж сохраняет собственную инициативу и обычные действия. По умолчанию корабль игроков не получает отдельного хода; для корабля с критическим повреждением предусмотрено исключение ради проверки целостности корпуса.

> **Проект, разработанный с помощью ИИ.** Есть автоматические тесты и локальные проверки интерфейса. Сделайте резервную копию мира и сначала проверьте модуль на копии. Файлы системы не изменяются.

> **1.5.1 — тактическое обновление.** Добавлены автоматический выбор объекта действий на Sensor Map и ручной выбор правой кнопкой, сортировка состава боя и интерактивное руководство. Map-only листы поддерживают редактирование Мастером, нативные условия и пересчёт характеристик без создания World Actors. Матрица A–K в Foundry 14.370.0 / SF2e 1.7.1 прошла 47/47 с независимыми клиентами Мастера и игрока на integration head `2849e2a`; последующие исправления CodeRabbit покрыты автоматическими регрессиями и не проверялись повторно в живом мире. Доказательства и ограничения см. в [заметках 1.5.1](docs/releases/1.5.1.md). Эта подготовка не создаёт тег, не публикует релиз и не выполняет merge.

## PF2e + SF2e Anachronism

Тот же модуль можно использовать в **PF2e 8.6.0+** с установленным и активным **SF2e Anachronism 2.4.0+**, на Foundry v14. Anachronism обязателен только в PF2e; в самостоятельной SF2e дополнительных модулей не требуется. Манифест поддерживает обе системы, а условная зависимость проверяется при запуске, чтобы не требовать PF2e-модуль в мире SF2e.

1. Установите официальный SF2e Anachronism из [релизов репозитория системы](https://github.com/foundryvtt/pf2e/releases).
2. Включите Anachronism и этот модуль, затем перезагрузите мир.
3. Используйте компендиумы папки **Tactical Starship Combat (PF2e)**. Их имена имеют суффикс `-pf2e`, ID соответствующих документов сохранены. Исходные SF2e-паки и UUID существующих миров не изменены.
4. Создавайте корабли через интерфейс модуля или импортируйте из PF2e-паков. Назначайте в экипаж персонажей PF2e: Computers и Piloting добавляет Anachronism через дополнительные навыки. Если навыки недоступны, модуль сообщает об этом, а не подменяет их другими.

Листы, станции, сенсорная карта, проверки, урон, инициатива критически повреждённого корабля и необязательная интеграция урона с Toolbelt используют namespace активной системы. Картинки и внутренние ссылки PF2e-паков ведут в PF2e-варианты. Приоритет имеют состояния самой PF2e; при наличии используются и дополнительные состояния Anachronism.

Это **не** конвертер миров между системами и не перенос уже импортированных SF2e-документов в PF2e. Сделайте резервную копию и используйте паки нужной системы. Выполняются статические проверки и мок-тесты; совместную работу в настоящем мире PF2e + Anachronism ещё нужно проверить в игре.

## Toolbelt и Workbench

Проверки корабля доступны через штатный `actor.getStatistic`. Адаптер предназначен для запросов Стойкости, Рефлекса и Воли через ссылки SF2e и **PF2e Toolbelt Target Helper** как у кораблей игроков на базе vehicle, так и у NPC-кораблей. Восприятие и сохранённые навыки используют тот же адаптер, что и лист корабля. Для спасброска корабля выбирайте **токен корабля**, а не члена экипажа.

Связующий слой сохраняет прежний метод поиска и дополняет его только для акторов с явной меткой корабля модуля. Обычные акторы, неизвестные характеристики и настройки сторонних модулей не изменяются. Проверки используют текущие данные экипажа и эффектов; системные модификаторы NPC сохраняются. Дополнительные броски и автоматическое применение урона не создаются.

При активном **PF2e Toolbelt** в сообщениях типизированного урона для кораблей модуля появляются две кнопки:

- **Урон через щиты**: расчёт корабельным движком, остаток после щитов переходит в корпус.
- **Напрямую в корпус**: щиты пропускаются, но применимые иммунитеты, сопротивления, уязвимости и Твёрдость сохраняются.

Штатные кнопки положительного урона (полный, половина, двойной и тройной) в строках корабельных целей тоже используют корабельный движок, по умолчанию через щиты. Множитель выбирается явно; **Shift** при применении открывает ввод числовой поправки. Типы и значения берутся из сохранённого броска, а не из присланной клиентом суммы. Для нескольких типов сначала учитываются защиты каждого типа, затем Твёрдость и переход щиты/корпус применяются один раз. Повторное применение того же броска сообщения к тому же кораблю защищено от повторного списания, в том числе при смене режима. Нужны активный ведущий и право изменять очки этого корабля.

Ручные ×2/×3 изменяют урон, но **не подтверждают критическое попадание**. Подтверждение попадания берётся из степени исходного сохранённого броска либо однозначного нативного результата урона атаки; критический успех спасброска/другой проверки не является критическим попаданием. Отсутствующие или противоречивые данные не подтверждают его. Собственный критический провал спасброска корабля тоже усиливает Compromised: существующая обработка спасбросков цели сохранена; неоднозначный случай Toolbelt следует проводить через явное нанесение урона Мастером, а не выводить из ×2. Типы урона, защиты и квитанции повторного применения сохранены.

Обычные акторы и штатное лечение сохраняют прежнее поведение. Личный **Блок щитом** Toolbelt не является действием корабельных щитов — используйте две корабельные кнопки. Общая строка со смешанным выбором кораблей и обычных акторов блокируется: используйте отдельные строки целей Toolbelt или выбирайте корабли отдельно. Карточки продолжительного урона используют сохраняемые квитанции модуля, а не обычные кнопки положительного урона. Невычисленные кости продолжительного урона, броски только лечения и сообщения с отдельным уроном по области всё равно требуют подходящего ручного способа; состояние продолжительного урона автоматически не создаётся.

Карточки атак самого модуля сохраняют прежнюю кнопку **применения урона**. У новых связанных бросков скрыты дублирующие системные кнопки. Для старых сообщений, созданных до обновления, не применяйте урон обоими способами. После установки перезагрузите мир.

В текущем аудите изучены исходники Toolbelt **3.60.0**; прежние заметки относятся к **3.59.2** и Workbench **7.7.5**. Автоматизация заклинаний и существ Workbench не заменяет движок корабельных действий: автоматическое выполнение станций и CR-масштабирование корабельных данных не добавлены. Обязательных зависимостей от этих модулей нет. Мок-тесты и локальные проверки интерфейса не заменяют проверку интеграции в игровом мире.

## Установка

В **Add-on Modules → Install Module** вставьте ссылку на manifest:

```text
https://github.com/Huxtuntios/sf2e-tactical-starship-combat/releases/latest/download/module.json
```

Эта ссылка заработает после публикации обычного релиза, не помеченного как prerelease. Эта подготовка не публикует 1.5.1. После разрешённой публикации можно использовать manifest конкретной версии:

```text
https://github.com/Huxtuntios/sf2e-tactical-starship-combat/releases/download/v1.5.1/module.json
```

Включите модуль в мире SF2e. Руководство есть в компендиуме **Guide / Руководство**.

При ручной установке создайте папку `Data/modules/sf2e-tactical-starship-combat/` и распакуйте **`module.zip` внутрь неё**. Файл `module.json` должен лежать непосредственно в этой папке. Автоматические архивы GitHub **Source code** предназначены для разработки, а не установки в Foundry.

Идентификатор модуля не меняется: `sf2e-tactical-starship-combat`.

## Быстрый старт

1. Создайте корабль игроков через **Starship Builder** либо преобразуйте актёра `vehicle` через контекстное меню. Обычные транспортные средства автоматически не преобразуются.
2. Импортируйте корабли НИП и опасности из браузера контента или компендиумов.
3. Перетащите персонажей на вкладку **Станции**, назначьте экипаж и посты.
4. Запустите мастер **Start Tactical Starship Combat**: корабли, экипаж, статусы обнаружения, опасности и объекты.
5. Бросьте инициативу как обычно. Действия доступны на сенсорной карте, во вкладке **Станции** и в отдельном окне **Действия станций**.

## Возможности

- **Две карты в одном бою:** обычная сцена корабля и отдельная зональная сенсорная карта с дальностью, курсом, областями и обнаружением.
- **Станции и экипаж:** пульт пилота, генератор, орудийная станция, сканеры, магический канал, пульт дронов и пользовательские станции. Отдельный менеджер показывает назначения и готовность.
- **Действия станций:** данные хранятся отдельно от интерфейса, проверки используют штатные средства SF2e. По умолчанию нарушения правил вызывают предупреждение; можно включить строгий режим. Неподдерживаемые способности остаются для ручного решения.
- **Корабельный урон:** щиты, корпус, иммунитеты, сопротивления, уязвимости, критическое повреждение, разрушение и целостность корпуса. Для учёта щитов используйте инструменты модуля, а не системные кнопки применения урона.
- **Опасности:** простые срабатывания и сложные рутины, ручные подтверждения ведущего или автоматический режим. Автоматизируются только поддерживаемые форматы правил.
- **Контент:** 74 корабля, 32 опасности, 39 действий, 17 орудий, 34 записи улучшений и три рамы; компендиумы на английском и русском. Для улучшений проверяются совместимость и вместимость станций, но не все их эффекты автоматизированы.
- **Оформление сенсорной карты:** цвета текста, арты и символы, отдельные изображения объектов и фон с прозрачностью, обесцвечиванием и размытием. Неопознанные контакты не раскрывают свои арты.
- **Темы окон:** все окна модуля используют клиентскую настройку «Тема интерфейса модуля»: «Как в Foundry», «Светлая» или «Тёмная». Предыдущий выбор светлой или тёмной темы сохраняется; другие клиенты независимы.
- **Длительность эффектов:** начало/конец определённого хода, несколько раундов, ручное подтверждение условия и напоминания о поддержании. Уклонение показывает потраченные действия; поддержание не тратит действия автоматически.
- **Единые эффекты и продолжительный урон:** ведущий выбирает весь корабль, механики, станции, действия, оружие или членов экипажа. Для каждого типа продолжительного урона выбирается сильнейший эффект; сохраняются квитанции, явное применение ведущим и упорядоченное восстановление.
- **Нативное управление состоянием:** доступны действия «исправен»/«уничтожен» и native Condition Manager. Общего Undo и history UI нет; сохранена только узкая guarded Toolbelt-квитанция отмены одного применения урона.
- **Интерактивные описания:** состояния отправляются в чат и перетаскиваются на персонажей с сохранением степени; урон бросается с нужным типом, без автоматического применения. Контекстные КС используют характеристики оператора, когда это однозначно следует из правил; отсутствующие и неоднозначные КС остаются для ручного выбора.
- **Удобство:** запоминание размеров окон и вкладок на клиенте, поиск по справочникам и улучшениям.
- **Сетевая работа:** изменения проверяет и сохраняет активный ведущий; права на корабль и станцию перепроверяются. `socketlib` не нужен.
- **Признак `starship`:** хранится и отображается на английском независимо от языка интерфейса.

## Эффекты Мастера и продолжительный урон (1.4.0)

Откройте **Эффекты корабля** на вкладке обзора листа или в карточке контакта сенсорной карты Мастера, включая приватный корабль. Нажмите **Применить эффект**, настройте параметры и перейдите в отдельное окно выбора целей. До окончательного подтверждения ничего не применяется; отмена сохраняет исходное состояние.

- **Состояние:** выберите поддерживаемое системное состояние или состояние корабля и степень, если она нужна. Для корабля принимаются только состояния с проверенной механикой; несовместимый выбор отклоняется, а не добавляется лишь для отображения. Состояния экипажа создаются штатными предметами системы с её проверками применимости.
- **Бонус / штраф:** выберите характеристику, числовое значение со знаком и системный тип (состояния, обстоятельства, предмета или без типа), затем область: только проверки, только КС или обе. Эффект изменяет реальные броски и поддерживаемые защитные характеристики, а не только текст листа.
- **Цели:** по умолчанию отмечен **Весь корабль**, но это не включает экипаж. Снимите отметку для независимого выбора проверок характеристик, навыков/проверок, атак, спасбросков, КД или других поддерживаемых защитных КС; установленных станций, их отдельных действий, всех атак орудий или конкретных орудий; всего экипажа или отдельных зарегистрированных/назначенных участников. Другие защитные КС выбираются отдельно от КД и спасбросков. Цели объединяются: один эффект не учитывается дважды для одной механической цели. Посторонние акторы мира в список экипажа не попадают. Отдельной защитной характеристики орудия сейчас нет, поэтому эта область недоступна. Пустые, устаревшие и несовместимые цели отклоняются.
- **Игнорировать иммунитеты целей:** только для Мастера, по умолчанию выключено; выбор сохраняется для этого применения. Обходится лишь иммунитет к самому эффекту. Данные иммунитетов, ограничения применимости и системное сложение модификаторов не изменяются; при последующем уроне иммунитеты, сопротивления и уязвимости продолжают работать. Отказ системы для конкретного участника показывается отдельно; успешные получатели сохраняются.
- **Просмотр / удаление:** менеджер показывает параметры, сохранённые названия целей, состояние связанных предметов и длительность. Удаление убирает только это применение и его собственные предметы экипажа, даже после переназначения участников; посторонние одноимённые предметы остаются. В бою доступны прежние настройки длительности. Бессрочные ручные эффекты не исчезают при завершении боя.

Для **продолжительного урона** задайте формулу костей (`NdM`, при необходимости плюс/минус целое число, например `1d6+2`), тип урона текущей системы, КС прекращения (по умолчанию **15**) и признак исходного критического попадания. Для корабля действует самое сильное ожидаемое значение каждого типа; разные типы бросаются отдельно, но применяются одним одновременным пакетом. Защиты учитываются по типам, затем Твёрдость и переход щиты/корпус — один раз. Исходное критическое попадание масштабирует урон, но не делает каждый следующий интервал новым критическим попаданием.

В бою урон обрабатывается в конце собственного обычного хода корабля. Если такого хода нет, используется **одна корабельная обработка в конце раунда**, а не после каждого члена экипажа; ход проверки целостности критически повреждённого корабля не добавляет обработку продолжительного урона. Вне боя **Бросить вне боя** использует текущее игровое время; повтор в тот же момент не перебрасывает кости. Для следующего интервала продвиньте игровое время.

Бросок сохраняет ожидающую квитанцию. Мастер явно **применяет пакет урона**, и только затем выполняет проверку прекращения. Повторное применение, другой элемент управления Toolbelt и перезагрузка используют ту же квитанцию. Успешная проверка корабля прекращает все его эффекты этого типа, включая подавленные, но не эффекты экипажа. Члены экипажа используют штатный продолжительный урон и собственные независимые проверки прекращения. Удаление одной строки отличается от прекращения всех корабельных эффектов одного типа. Удалённые или закончившиеся системные предметы не создаются заново. Неподдерживаемые правила состояний и способности НИП без Удара остаются ручными.

Поддерживаемые компоненты продолжительного урона Ударов НИП сохраняются отдельно от немедленного урона как в прямом, так и в отложенном процессе. Ручной Drone Shield Protocol остаётся ручным. Границы реализации и фактически выполненные проверки указаны в [решениях по правилам](docs/rules-decisions.md), [описании программного интерфейса](docs/api.md) и [заметках 1.4.0](docs/releases/1.4.0.md).

## Ограничения

Полный многопользовательский сценарий в живом Foundry ещё требует проверки. Штатное применение урона SF2e не учитывает щиты модуля. Многие улучшения и способности НИП требуют решения ведущего. Продолжительный урон применяется только через сохраняемые квитанции ведущего; устаревшие или уже восстановленные получатели и повторное применение блокируются. Общего Undo и history UI нет. Неподдерживаемые нативные условия/механики, удалённые привязки ходов и нестандартные перестановки инициативы могут потребовать ручной корректировки. Для изменения состояния нужен активный ведущий. Учёт действий и реакций не ведётся.

Приватность контактов Sensor Map и производительность в настоящем Foundry не проверены. Большие изображения отображаются через PNG-копию с пределом 4096 пикселей; исходные файлы и пути не изменяются. Первичное декодирование и ограничения доступа к холсту могут привести к использованию полного исходного изображения. Локальная проверка PNG 8100 × 11700 и 360 объектов — не профилирование Foundry. Для незавершённого опознания есть явная кнопка восстановления Мастера; перед повтором разберите конфликт. Таймаут не отменяет операцию ведущего, которая могла уже сохраниться.

Toolbelt проверен по исходникам и моками, но не в настоящем Foundry. Объединённые, дополненные и разделённые карточки урона Better Chat не применяются к кораблям автоматически: ведущий сверяет исходные карточки и решает вручную.

## Разработка

Нужны **Node.js 22.13+** и npm. Bash и отдельный архиватор не требуются.

```sh
npm ci
npm run format
npm run check
npm run build:release
```

В `dist/` появятся `module.json`, `module.zip`, контрольные суммы и заметки к выпуску. Для локальной проверки интерфейса:

```sh
npx playwright install chromium
npm run test:ui
```

Скомпилированные компендиумы, зависимости и архивы не коммитятся. Исходные данные находятся в `data/`; перед сборкой компендиумы создаются заново. GitHub Actions проверяет проект и собирает файлы релиза.
