## Архитектура и влияние до правки

UI `action-runner` → `executeAction` → `executeDroneMovement` → `patchStarship` (очередь по UUID на активном GM) → флаг Actor → `recordChange` и отдельная карточка. Данные сохраняются в существующем `drones`, без нового списка. `stageDroneBlock` работает в Draft цели и выполняет ожидаемое сравнение перед записью. Изменения затрагивают проверки идентичности и превью, не структуру данных и не API Foundry/SF2e; необходимы тесты старых записей, вместимости после изменения станции, повторов, прав и Drone Block. Очередь действует в процессе активного GM, а не является доказанной распределённой транзакцией.

Foundry manifest заявляет минимум 14.361, SF2e 1.6.0 и PF2e 8.6.0 с Anachronism; конкретная локальная установка Foundry/SF2e и живой мир не доступны. Три прямые страницы AoN из задания возвращают HTTP 403. Локальные тексты и индексированный фрагмент AoN не позволяют утверждать, что правила всех улучшений подтверждены. Не автоматизировать непроверенные правила. Резервная копия мира необходима перед испытаниями.

## Реализованные изменения

- Deploy проверяет текущую вместимость и неоднозначные старые/осиротевшие привязки. При переполнении Retrieve по-прежнему работает. Это консервативная техническая защита, а не утверждение о дополнительном правиле Tech Core.
- Deploy/Retrieve и добавление больше не выбирают произвольно первую запись при одинаковых ID дронов; повторяющийся ID станции также запрещён. Размещение мины и базовый Drone Block отклоняют неоднозначный ID дрона; повтор с неоднозначным ID мины тоже отклоняется.
- Превью и список Deploy/Retrieve используют те же проверки состояния, включая доступность после cooldown. Игровая запись по-прежнему проверяется на стороне активного GM. Никаких новых системных API или миграций нет.
- Добавлены семь unit/mock-тестов, в том числе на сохранность старых полей, отсутствие записи/истории/карточки при отказе, одновременные запросы и неизменяющее состояние превью.

## Выполненные проверки и их границы

- `npm ci --no-audit --no-fund` на Node v24.22.1; зависимости установлены, однако npm предупредил об установочном скрипте classic-level. Сборка паков и тесты ниже выполнены успешно.
- `npm run check` — форматирование, ESLint, валидация содержимого, генерация паков, **446/446** unit/architecture тестов, 0 пропусков. Проверки модели и сокетов используют mock Foundry, не настоящий сервер.
- `CHROMIUM_PATH=/usr/local/bin/chromium npm run test:ui` — **41/41** браузерная фикстура. Это не запущенный Foundry; отдельной визуальной приёмки новых состояний в Foundry не было.
- Настоящие Foundry v14, SF2e, PF2e + SF2e Anachronism, разные клиенты, отказ/смена GM и приватность не проверены: среды нет. Значения compatibility в manifest сохранены без повышения и не являются новым доказательством совместимости.
- HTTP 403 при открытии трёх прямых страниц AoN, перечисленных в задании; индексированный [builder AoN](https://2e.aonsrd.com/tactical-starship-combat/builder) лишь частично подтверждает отдельные сведения. Полный источник правил отсутствует; не подтверждённые механики не выдаются за реализованные.

## Что не завершено

Нет полной реализации Repair/Scramble/Pyrotechnics, Shield Protocol, Mine Deployment Shell, Pet Drone Shell и связанной с персонажем экономики действий. Детонация/модификация мин, универсальная проверка чата/no-op и карточек, все типы модификаторов, полный аудит интерактивных описаний, GM Override/корпусов, приватности и Undo, а также реальная multiplayer-приёмка остаются открытыми. Очередь живёт в процессе активного GM; она не доказывает корректность переключения GM. Повтор старого Deploy после промежуточного Retrieve не имеет устойчивого request receipt и может снова изменить состояние. Сенсорная карта хранит данные в общих флагах и не является безопасным хранилищем секретов. Известные ограничения dev.1 сохранены.
