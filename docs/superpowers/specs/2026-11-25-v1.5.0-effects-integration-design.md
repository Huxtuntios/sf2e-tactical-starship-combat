## 1. Goal

Integrate the complete v1.4.0 unified starship effects and persistent-damage subsystem into the native-first reconstruction without losing its newer targeting, hazard, plasma, Sensor Map, condition-manager, card, and localization work.

The integration must preserve one authoritative starship state under `flags.<module>.starship`, one damage application path, native Foundry/SF2e contracts where verified, and the existing public API compatibility contract.

## 2. Non-goals

- No release publication, tag, merge to `main`, or external deployment without separate authorization.
- No restoration of the removed general Undo or change-history UI.
- No second persistent effect store or competing damage adapter.
- No downgrade of `main`; the integrated branch targets version `1.5.0`.
- No broad redesign of unrelated Sensor Map, targeting, plasma, hazard, or chat-card behavior.

## 5. Additive Data Contract

Existing effects remain valid. The following optional fields are added or normalized on read:

- Manual effect record: `manual`, `kind`, `targets`, `ignoreImmunities`, `nativeTargets`, `conditionValue`, `persistent`, `status`, `targetSnapshot`, `rejectedTargets`, `shipPersistent`, `shipRecovered`.
- Ship state: `effectOperations`, `persistentStrikeOperations`, `persistentDamageReceipts`, `persistentDamageSequence`.

No existing effect, Actor, Item, Combat, flag, or document ID is deleted or rewritten by a schema migration. `DATA_VERSION` is not increased for these optional fields.

## 6. Manual Effect Flow

1. The GM configures an effect in the combined Effect Manager.
2. The target dialog captures Entire Starship, mechanics, stations, actions, weapons, and crew recipients.
3. `applyManualEffect` sends a validated payload to the active GM.
4. The application service validates the current catalog and modifier contexts.
5. A pending record is stored through the per-ship queue.
6. Native crew Items are created only for supported recipients and selectors.
7. The record becomes `active`, `partial`, or `failed`; rejected recipients remain explicit.
8. Reusing the same `operationId` and configuration is idempotent. Reusing it with a different configuration is an operation conflict.

Removal deletes only native Items linked to the module application record, then removes the module record. Actor deletion and combat-end cleanup use the same ownership checks.

## 7. Persistent Damage Flow

1. A strike supplies persistent damage parts and source metadata.
2. `stagePersistentDamage` creates idempotent persistent effect records in the same `Draft` as the strike.
3. At the correct ship interval, the strongest effect of each damage type is selected by native expected value.
4. Native persistent dice are evaluated once and stored in a durable receipt.
5. The GM applies the pending receipt through the existing starship damage engine exactly once.
6. The receipt stores applied component IDs, result, actor, and sequence.
7. Ship recovery is accepted only after the latest same-type receipt has been applied.
8. Crew recovery delegates to the native Item `rollRecovery` method.

The interval is the ship's ordinary turn, or one ship-level end-of-round fallback when the ship has no ordinary turn. Crew turns and compromised hull-integrity turns do not create extra ticks. Outside combat, processing uses current world time.

## 8. Statistics and Effect Merge Rules

- Manual scoped effects use `matchesEffectScope`; unscoped legacy effects retain their existing behavior.
- Native condition modifiers are included once. The ship Statistic adapter must not add the same modifier again as a module delta.
- `station-check` contributions remain available to Strike target validation and attack previews.
- `ac-against-strikes` and `reflex-against-area` aliases apply only in their verified contexts.
- Hazard helpers continue to use native hazard AC, saves, HP, hardness, and IWR.
- Sensor range remains derived and nullable; effect integration must not invent a range.
- Existing target/detection/private-contact checks remain authoritative before effect or damage execution.

## 9. UI and API

The combined Effect Manager includes:

- v1.4.0 add/configure/target/remove/timing controls.
- Persistent receipt process/apply/recover controls and statuses.
- Current `Исправен` and `Уничтожен` actions.
- Current native condition add/remove controls.
- No history UI and no general Undo.

The Starship Sheet and Sensor Map public/private detail open the same manager. The target dialog is a separate ApplicationV2 form with localized labels, live summary, keyboard-accessible controls, and explicit apply/cancel.

Additive API methods:

- `applyManualEffect`
- `removeManualEffect`
- `getEffectTargetCatalog`
- `processPersistentDamage`
- `applyPersistentDamage`
- `recoverPersistentDamage`
- `openEffectManager`

## 10. Error Handling and Concurrency

- All state-changing effect and persistent-damage operations are active-GM only.
- Per-ship queues serialize effect operations; persistent damage uses the same ship serialization key as actions.
- Native crew item creation/removal is serialized per recipient Actor.
- Stale targets, stale receipts, incompatible selectors, foreign Items, and operation conflicts fail explicitly.
- Partial native application is preserved and reported; it is not represented as full success.
- Failed persistent rolls leave a failed receipt and do not apply damage.
- No blind retry is performed after timeout or uncertain write results.

## 11. Testing Strategy

Implementation is test-driven by layer:

1. Effect scopes and native adapter.
2. Manual application service and target catalog.
3. Persistent staging, receipts, application, and recovery ordering.
4. Shared `effects`/`stats` merge.
5. Damage and action-engine staging.
6. Combat timing and cleanup.
7. Toolbelt/native card routing.
8. Combined Effect Manager and target dialog UI.

The v1.4.0 suites are ported and adapted, including manual application, native adapter, persistent damage, effect calculations/UI, target validation, station-check Strike, and rule enforcement.

Required regression gates:

- Current full unit/integration/architecture suite.
- Current UI fixture suite.
- Hazard targeting, native hazard saves/AC/HP, Area Fire, and plasma saves.
- Plasma multi-target damage and replay guards.
- Sensor Map range/detection/private projections and map-only repeated drops.
- Native KeyT targeting and visible target marker.
- Card degree-of-success rendering.
- Crew weapon proficiency requirement `8.1`.
- Operational/destroyed and native valued condition behavior.

UI fixtures cover EN/RU manager and target dialog at 1100/600/380 px, persistent receipt cards, and Sensor Map/detail entry points.

## 13. Acceptance Criteria

- Full v1.4.0 manual effect and persistent-damage behavior is available in the native-first module.
- Existing native-first targeting, hazard, plasma, Sensor Map, card, condition, and localization behavior remains green.
- No duplicate condition/effect modifier application exists.
- Persistent damage is applied once and recovered only in the valid order.
- Native crew effects are created and removed only for supported, owned recipients.
- Existing world documents and IDs remain valid without destructive migration.
- Version `1.5.0` chore, release notes, ZIP, and checksums are reproducible.
- The final PR is based on current `main` and contains no publication/tag/merge action.
