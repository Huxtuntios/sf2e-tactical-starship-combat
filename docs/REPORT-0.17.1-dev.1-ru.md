# Отчёт: 0.17.1-dev.1

Экспериментальная версия для тестового мира, основана на исходном архиве 0.17.0. Это не готовый релиз: сделайте резервную копию мира перед установкой. Архивы предыдущих версий не изменялись. Commit, push и GitHub Release не выполнялись. Ссылки manifest/download в пакете указывают на ещё не опубликованный релиз; устанавливайте ZIP вручную.

## Перетаскивание Actor на Sensor Map

- Поддержаны Actor со стандартным флагом корабля модуля и Actor типа `hazard`; источники — каталог Actors и Actor Compendium. Новый объект ссылается на UUID исходного документа, без создания копии Actor, токена, Combatant или инициативы.
- Запрос обрабатывает активный GM: проверяет пользователя, разрешает UUID повторно, проверяет тип документа и зону. Последовательная обработка запросов карты организована в пределах конкретного боя. Повторный перенос уже имеющегося объекта перемещает его, сохраняя оформление; перенос в ту же зону не записывает состояние. Если в старой карте уже несколько совпадений, запрос отклоняется.
- **Секретные Hazards и корабли не защищены.** Полное состояние текущей карты хранится в общих флагах Combat и может быть доступно клиентам; скрытие в интерфейсе не является защитой данных. Чтобы не обещать ложной защиты, добавление нового объекта требует явного подтверждения его публичного раскрытия. Старые скрытые записи не мигрированы и также могут раскрывать данные. Не храните секретную информацию на этой карте. Для настоящей приватности нужны отдельное хранилище с правами доступа и переработка представления, обнаружения и синхронизации.
- Compendium Actor остаётся ссылкой на оригинал и может быть недоступен для записи или изображения на клиенте; боевые операции с таким Actor не проверены. При необходимости импортируйте Actor в мир до использования.

## Центрирование и Auto Mirror

Ранее визуальный контейнер имел выравнивание к началу и занимал фиксированные колонки сетки даже без стрелки; это смещало изображение. Если стрелки нет, визуальный блок теперь занимает ширину карточки и центрирует изображение или резервную иконку. Несколько объектов сохраняют отдельные карточки: ни позиция объекта, ни зона не изменяются. Поведение в локальных браузерных фикстурах проверено; реальные масштабы и размеры окна Foundry ещё нужно проверить.

Используется существующая настройка Auto Mirror. Она сравнивает фактический игровой курс влево/вправо с базовой ориентацией изображения, а автоматальное и ручное отражения по горизонтали складываются через XOR. Вертикальное отражение и поворот независимы; скрытие стрелки Auto Mirror не отключает. Для новых объектов исходная ориентация изображения задаётся как «Неизвестно» — GM должен выбрать её явно. Неизвестный курс не угадывается: его можно задать в инструментах GM карточки объекта. Для корабля в мире изменение Actor и карты выполняется двумя записями, не атомарно; Actor из Compendium не изменяется. Древние объекты сохраняют прежние значения по умолчанию. Автоматического отражения по направлению вверх/вниз нет, поскольку игровой курс модели только горизонтальный.

## Категория и степень владения оружием

Проверены все 17 канонических записей `data/equipment/weapons.json` и построение Compendium: 7 simple, 6 martial, 4 advanced. Генератор записывает категорию в `Item.system.category`; в этих исходных записях нет отдельного `requiredProficiency`. Категория не равна рангу владения персонажа, поэтому не выводится вымышленный ранг. Общая функция показывает категорию отдельно и, если явный ранг предоставлен в данных записи, отображает `untrained`, `trained`, `expert`, `master` или `legendary`. Установленное оружие с `weaponRef` получает отсутствующие данные из каталога, без переписывания старых записей. Для пользовательских/неизвестных значений остаётся локализованное «не указано», а не `undefined` или `[object Object]`.

Ограничение: это не полное чтение произвольно изменённых записей внешних Compendium при отображении установленного оружия: при ссылке на каталог используются данные каталога проекта, а не живое разрешение каждого Item. Работа с импортированными и пользовательскими записями в реальном Foundry требует проверки.

## Проверки

- `npm run check`: форматирование, ESLint, валидация данных, сборка compendiums и **439/439** unit/architecture-тестов успешно. Тесты охватывают все штатные категории оружия, права и проверки GM в моках, отказы и отсутствие повторной записи, сериализацию запросов и назначение начального курса.
- `CHROMIUM_PATH=/usr/local/bin/chromium npm run test:ui`: **41/41** локальных браузерных проверок успешно, включая DOM-обработчики переноса, подтверждение и отмену, компоновку и Auto Mirror. Это фикстуры, а не Foundry.
- `npm run build:release`: сборка установочного ZIP и compendiums; целостность обоих архивов проверяется отдельно при упаковке.
- В реальном Foundry VTT, SF2e и на нескольких настоящих клиентах эта версия **не проверялась**. Ручные результаты ранее проверенных версий к ней автоматически не относятся. Установочный пакет должен быть проверен в тестовом мире.
- `.git` в исходном архиве отсутствует. Вместо невозможного `git diff` выполнено сравнение с распакованным архивом 0.17.0 без `node_modules`, сборок и compendiums; итоговый diff пользователь может просмотреть в GitHub Desktop.

## Ручной план приёмки в Foundry

Проверить перенос кораблей игроков и NPC и Hazards из каталога и компендия, неподдерживаемые Actor, повторные переносы и отсутствие дублей. Проверить отказ игроку и поведение при отсутствии/смене активного GM. На двух клиентах проверить перемещение, обновление изображений и повторный рендер; **не использовать секретные объекты**. Проверить скрытую стрелку, разные масштабы, несколько объектов, включённый/выключенный Auto Mirror, сочетание с ручными отражениями и повторной сменой курса. Сверить 17 видов оружия, импортированные, старые и пользовательские записи. Для всех этих сценариев результаты автоматических фикстур не доказывают поведение Foundry.

Ранее отмеченные незавершённые задачи по действиям и улучшениям дронов, полный аудит чата/no-op, GM Override и корпусам, приватности журнала, сокетам, Undo и реальному профилированию больших фоновых изображений остаются открытыми; эта версия не устраняет их целиком. По пользовательскому наблюдению очень большое изображение 8100 × 11700 может вызывать зависания.
