## Included behavior

- Automatic Sensor Map action-object selection follows the exact current world Actor, map-only placement or hazard and clears for crew turns or missing objects. A client toggle controls automatic tracking; right-click selection provides an explicit GM override that persists while automatic tracking is disabled.
- GM and player pre-targeting before an action through Sensor Map pointer selection and English KeyT, with Shift additive selection, visible target markers and matching detail refresh.
- Display-only level/name sorting in the Start Tactical Combat roster. Sorting does not write Actors or alter selections, source data or the encounter draft.
- An interactive eight-section onboarding guide with singleton window behavior, per-user auto-open suppression, manual reopen, minimize/restore, English/Russian content and English fallback for unsupported languages.
- Editable GM map-only snapshot sheets for supported basics, backed by the private serialized snapshot store rather than World Actors. Non-GM writers are rejected.
- Snapshot-backed native condition Items, exact valued-condition updates, a cached prepared ActorClass view and refreshed Effect Manager/public labels after writes.
- Preserved native-first targeting, action/attack/save flows, Sensor Map privacy, persistent damage, Toolbelt card routing and existing module/pack/document IDs.

## Actor/sheet audit and fixed problems

The read-only Actor/sheet audit identified four map-only defects before integration. All were fixed with regression coverage and live retests.

| ID  | Confirmed problem                                                                               | Final behavior                                                                                                                                                                                       |
| --- | ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Snapshot sheets were transient/read-only and supported basics were not durably editable.        | The active GM can edit name, HP, AC and level through the system sheet and Save to the snapshot store. The same sheet and Sensor Map refresh; no World Actor is created; non-GM writes are rejected. |
| D2  | Map-only snapshots lacked native condition/effect mutation APIs exposed by Effect Manager.      | Snapshot-backed embedded Items add/change/remove native conditions with exact values and persisted readback; manager state reads the current store.                                                  |
| D3  | Snapshot Actors could ignore native prepared conditions/modifiers and fall back to a plain d20. | A cached prepared ActorClass view is rebuilt after writes, so native statistics, roll options, immunities and native rolls recalculate without persisting derived data.                              |
| D4  | Open snapshot sheets became stale and repeated opens could duplicate windows.                   | A stable per-placement document/sheet registry reuses one window, refreshes after updates and closes/removes the entry when the snapshot is deleted.                                                 |

The earlier forced-read-only D1 commit was superseded by the editable snapshot-backed implementation required by the maintainer.

Live testing also found and fixed valid transient Actor IDs, exact placement UUID preservation, map-only actor-basics persistence, public snapshot label synchronization, Effect Manager refresh, prepared-sheet rebuilds and valued-condition native creature semantics. The corresponding commits are `27e3341`, `7bd689e`, `7aa7368`, `779cd89`, `caaef96`, `0d0d8e7` and `2849e2a`.

## CodeRabbit follow-up

CodeRabbit reviewed release-preparation head `ea7844d` and the follow-up fix commits `c5dfda0`, `7237043`, `7e1abb7`, `4faaf5f` and `1f2c712`, posting 23 findings across five rounds. Twenty-two were confirmed and fixed in the same branch:

- Snapshot sheet cleanup unregisters before close, reports close failures without blocking contact removal, closes sheets whose record disappears and does not reopen a sheet removed during either close/delete ordering.
- Unchanged Combat updates preserve unsaved sheet input; per-placement writes and sheet refreshes are serialized so a rejected stale write cannot replace a committed actor.
- Native Item update/delete controls on the snapshot clone route through `SnapshotItem`; counter updates below the minimum delete the effect, and new timed effects receive current world-time plus origin-first initiative metadata.
- Snapshot refreshes are single-flight per placement, retain the newest record, isolate per-sheet failures, track the successfully configured record separately and resynchronize the actor even when the stored record returns to that configured state.
- GM pointer/KeyT pre-target lookup includes only resolvable hidden/observed private projections and excludes undetected, pending-reveal or unprojected contacts.
- Condition increments select the active prepared Item; valued vehicle conditions persist both increases and decreases through the snapshot Item API.
- Persistent-damage recovery removes only the selected damage type.
- Candidate condition/effect immunity is evaluated through native Item preparation, including persistent-damage roll options.
- Direct snapshot name/portrait edits are rejected while a reveal intent is pending.
- Onboarding suppression uses Foundry user scope, with matching English/Russian labels.
- The public-projection permission regression now resolves and opens the sheet as the owning player rather than as GM.

The remaining dock-render comment was not confirmed: the Combat refresh channel requests all parts (`sensorPartsFor("combat")` is `null`), and `gmActionSelection` does not render. No speculative UI change was applied.

These snapshot follow-up changes were added after the 47/47 live run and are covered by focused regressions plus the full automated gates below. They were not live-retested; the original live claims remain tied to integration head `2849e2a`.

## GM pre-action targeting follow-up

Manual testing found that GM pointer and KeyT selection were blocked outside an active targeting session by explicit GM-only early returns. Commit `a2f75e1` removes those guards and unifies the GM click path with the player path while preserving detail refresh, Shift additive selection, RMB action-object assignment and active targeting sessions.

The fix was live-verified in Foundry 14.370.0 with GM `Gamemaster2`: pointer selection marked a map-only target and opened its details; Shift added a second target without clearing the first; KeyT toggled the hovered target off while preserving the other. Both GM and Player3 consoles remained clean after reload, and cleanup restored 186 Actors, 1 Combat with 3 combatants, 11 Journals and the original two Sensor Map objects.

## Known limitations

- A live PF2e + Anachronism session was explicitly outside this task's scope and was not run.
- Foundry core logged expected minimum-window-size errors during deliberate 600 px and 500 px responsive probes. The window was restored to 1920×1080. No module runtime errors were observed, and the independent Player3 console remained clean.
- The live world was not restarted and Foundry was not upgraded. Runtime files were hot-copied with a backup and hash verification as authorized; the final 1.5.1 manifest bump changes no runtime code.
- The live matrix certifies only the recorded Foundry 14.370.0 / SF2e 1.7.1 environment and scenarios, not every declared system/dependency combination.
- CodeRabbit's final architecture review retained two inferred, unreproduced risks: an identity edit overlapping reveal-intent creation on separate queues, and retrying an Item creation after a later projection/sheet-refresh failure. No speculative fix was applied because neither path was reproduced and the remedies would broaden scope; inspect these paths before campaign-wide rollout.

## Installation

### Verified local artifact

1. Back up the target world and disable the currently installed module copy.
2. Use the locally built `dist/module.zip`.
3. Extract it into `Data/modules/sf2e-tactical-starship-combat/` so that `module.json` is directly inside that directory.
4. Enable **SF2e Tactical Starship Combat**, reload the world and verify the loaded version is `1.5.1`.
5. Review the single integration PR before campaign-wide rollout.

GitHub automatic source-code archives are development sources, not installable module packages.
